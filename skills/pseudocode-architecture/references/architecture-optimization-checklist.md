# Architecture optimization checklist — performance bottlenecks and redesign risks

Classify every class in both tables as applicable or N/A for this project's workload and deployment target,
each with a one-line reason, **per component** you partition in `SKILL.md` step 3. Table A covers performance
bottlenecks (system-level 1–8, library-usage 9–12); Table B covers structural decisions whose absence forces a
redesign after implementation.

## Table A — Performance Bottlenecks

| # | Class | Applies when | Fix at design time | Budget shape |
|---|-------|--------------|--------------------|--------------|
| A1 | I/O and network latency (disk/comm) | Files, sockets, or external APIs sit on a hot path | Sync vs async I/O model; batching/buffer sizes; serialization format; timeout/retry policy; cache layer and its invalidation rule | p95 round-trip ms per operation; sustained MB/s |
| A2 | Algorithmic CPU load | Input size can grow past trivial, or tight loops run per request/sample | Big-O of core operations against max expected n; data structure choice (hash/tree/array); precompute vs on-demand; parallel/vectorized applicability | worst-case ms at max expected n |
| A3 | Memory footprint and unbounded data loads (RAM swap/GC, missing paging) | Long-running process, large working set, GC runtime, or any query/read that can return more than the working set needs | Peak working-set estimate vs available RAM; streaming/paging/cursor access as the default with server-side filtering and column projection; hard row/byte cap per fetch; object lifetime and ownership model; pooling/arena where allocation rate is high | peak RSS MB; max rows or bytes per fetch; GC pause or allocation-rate ceiling |
| A4 | Database lock contention | Concurrent writers, or transactions spanning multiple statements | Transaction boundaries and isolation level; lock granularity; hot-row avoidance (queueing, sharding); indexes planned for write path, not only reads | max transaction hold ms; lock waits at target concurrency |
| A5 | Host-device transfer (PCIe bandwidth) | GPU, accelerator, or DMA peripheral in the data path | Transfer batching and compute/copy overlap (streams, double-buffering); pinned memory; data residency on device across kernels; compression/quantization at the boundary | transfer-to-compute time ratio; effective GB/s vs bus limit |
| A6 | Cache misses and branching (data locality) | Per-element cost matters: inner loops over large arrays, real-time paths | Memory layout (SoA vs AoS); access order matching storage order; hot data sized to cache levels; branch-free inner loops where the access pattern demands | ns per element; how miss rate will be measured (e.g. perf stat) |
| A7 | Concurrency model: sync overhead and blocking waits | More than one thread, process, or async task shares state, or library calls block a thread while downstream work could overlap | One concurrency model fixed project-wide (threads vs async vs processes); async or streaming API variants chosen per library up front; pipeline stages decoupled by bounded queues; shared-state inventory with an owner (lock or queue) per item; no blocking calls on event-loop threads; worker counts vs cores | lock-wait and idle-wait share of runtime; context-switch rate ceiling; end-to-end latency vs sum-of-stages ratio |
| A8 | Embedded interrupt and resource limits (MCU) | Firmware target with ISR deadlines, fixed RAM/flash, limited peripherals | ISR worst-case duration and priority map; DMA vs interrupt vs polling per peripheral; static allocation plan (no heap on ISR paths); per-module RAM/flash budget | ISR worst-case cycles; RAM/flash budget table |
| A9 | Heavy instance re-creation (missing object reuse) | A library client, session, connection, compiled object, or loaded model could be constructed per call or per request | Init-once lifetime for expensive objects (clients, sessions, prepared statements, compiled regex, models) with an explicit creation boundary; pooling where one instance cannot be shared; thread-safety of each shared instance stated | instantiations per N requests (amortized to startup); startup vs per-call cost split |
| A10 | Excessive type conversion and parsing (serialization overhead) | Data crosses format boundaries (JSON/ORM/DataFrame/DTO) more than once per flow | One canonical in-memory representation per flow with the conversion count fixed at design; validate schema once at the boundary, not per layer; zero-copy or lazy-parse options where the library offers them | conversions per request path; serialization share of runtime |
| A11 | Deep abstraction wrappers (proxy indirection overhead) | Framework middleware, ORM proxies, or decorator stacks wrap every hot-path call | Layer count per hot path fixed at design; a documented direct-API escape hatch for hot paths (e.g. raw query beside the ORM); middleware list audited per route/endpoint | wrapper depth on hot paths; overhead vs direct-call baseline |
| A12 | Untuned library defaults (connection/buffer sizing) | Hot-path libraries ship conservative defaults (pool size, buffer size, batch size, timeout) not matched to this workload | Enumerate each hot-path library's pool/buffer/batch/timeout settings and set them from workload numbers, recording the source of each number; never ship an unexamined default on a hot path | zero pool-exhaustion events at target concurrency; flush/retry rate ceiling |

## Table B — Redesign Risks

| # | Class | Applies when | Fix at design time | Evidence shape |
|---|-------|--------------|--------------------|----------------|
| B1 | Persistent data schema evolution | Any data outlives a process run: database rows, files, message formats | Version marker in every persisted shape; migration mechanism and when it runs; backward-compatibility policy (e.g. read-old/write-new) | migration exercised in a phase `Verify:` (write vN, upgrade, read) |
| B2 | Partial failure and recovery semantics | Multi-step operations can fail midway: network calls, multi-file writes, queues | Idempotency keys or upserts for anything retried; crash-restart point (checkpoint, journal, or recompute); delivery semantics chosen per channel (e.g. at-least-once + idempotent consumer); timeout and retry policy per external call | kill-and-restart test in a phase `Verify:` |
| B3 | Trust boundaries and auth placement | Any input crosses from an untrusted source: users, network, files | One validation point per boundary; authn/authz layer placement fixed before endpoints multiply; secrets never in code or logs | boundary map in the architecture doc; negative-input tests in `Verify:` |
| B4 | Testability seams | Multi-module project; critical when hardware, network, clocks, or randomness are involved | External dependencies injectable or fakeable at module boundaries; hardware access behind an interface with a host-runnable fake; clock and randomness injectable where logic depends on them | every phase `Verify:` runnable without unavailable externals, or explicitly marked hardware-gated |
| B5 | Single-node assumptions | Scale-out or multi-instance deployment is a requirement (otherwise N/A) | State externalized — no in-process session, cache, or lock as the only copy; filesystem use safe under multiple instances; work-distribution model chosen | two-instance smoke test in a phase `Verify:` |
| B6 | Observability seams | More than one component, or any async flow | Structured logs at module boundaries; correlation/request ID propagated end to end; metric list fixed at design — the Table A budgets are its core | log and metric field list in the architecture doc |
| B7 | Shutdown and resource lifecycle | Long-running process, or resources needing cleanup: files, connections, hardware states | Each resource has a named owner responsible for closing it; graceful-shutdown path and signal handling; startup dependency order | clean-shutdown check in a phase `Verify:` |
| B8 | Backpressure and overload behavior | Producer and consumer rates differ, or external callers are uncontrolled | Every queue bounded with an explicit full-queue policy (block, drop, or shed); rate limit at ingress; degradation mode defined instead of discovered | overload test at a stated multiple of target rate |
| B9 | Dependency boundary risk | A third-party library or service sits on a critical path | Versions pinned; heavy dependencies reached through one adapter module so replacement stays localized; maintenance status and license checked at selection time and recorded as a decision | dependency inventory in the architecture doc with each adapter's location |
| B10 | Configuration and secrets separation | Any value differs between environments or must not be committed | Config source hierarchy fixed (env vars, file, flags); secrets path defined; no environment-specific literals in code | config inventory; grep for hardcoded paths/URLs in a phase `Verify:` |
| B11 | Split ownership of a lent resource | A buffer, handle, or slot is lent across a component boundary and the lender can revoke it while the borrower still has work queued against it | One component holds the *authoritative* record of a lent resource's state; the boundary carries progress (counts, offsets, sizes) rather than the resource's identity, so clearing the owner's single field cancels every pending use with no second cancellation path to remember. Name that owner per resource, and make revocation a single funnel every terminal path must pass through | one field per lent resource whose clearing *is* the revoke; a revoke-mid-use test asserting no completion callback fires afterwards |
| B12 | Lifetime of a view into reused storage | A parser, decoder, or accumulator hands out pointers into scratch storage it will overwrite, and the consumer runs later than the emitting call (at block, frame, or message completion rather than per fragment) | State, per emitted view, whether it survives the emitting call. Where the consumer runs later, copy at emission into storage that outlives it and budget that storage explicitly; do not leave "valid until the next call" as an unwritten assumption | a fragmentation test: deliver identical input split into the smallest legal chunks and assert identical output. Single-chunk delivery cannot detect this class, which is why it survives hand-written tests |
| B13 | Contract claims about a dependency's behavior | An interface contract asserts what a third-party library, a sibling component, or the transport already does, and uses that assertion to justify not doing it here | Cite the dependency's own contract for every such claim, or verify it once and record where. Treat an unverifiable claim as false and do the work locally. This class is distinct from B9: B9 asks whether the dependency can be replaced, B13 asks whether what you believe about it is true | every "X already handles this" carries a citation; a round-trip test across that boundary rather than a unit test of one side. Following a wrong claim produces a bug, not a gap, so it does not surface as a missing feature |
| B14 | Boundary counterpart availability | A component's contract can only be exercised against an adjacent layer, device, or service that does not exist yet — an unimplemented sibling layer, external hardware, or a third-party server | Stand the counterpart up as a named component at design time: a scripted fake under the project's control, an official-implementation oracle, or both with the division of labor stated. Give each its own component-table row and tier estimate, and fix which contract behaviors it must honor faithfully (lifecycles, error paths, fault injection) versus merely script | counterpart named in the architecture doc's component table; every phase `Verify:` that exercises the boundary states which counterpart it runs against |

## Applying the checklist

For every applicable Table A class, fix the listed design-time decisions now, set a numeric budget, and name
the measurement command that will verify it. For every applicable Table B class, fix the listed structural
decision and record where its evidence check runs. Nothing stays open for implementation to improvise.

Every measurement command must be runnable, not aspirational: state what generates its load and test data
(existing tool, script, or fixture). When that requires a harness — load generator, benchmark script,
representative dataset — note it as a dependency, to be built no later than the point that first needs it. A
budget that can only be measured on a complete system (e.g. end-to-end latency at target concurrency) gets a
per-component micro-benchmark proxy plus a note naming the integration phase where the full measurement runs.

Numbers the checklist needs but the spec lacks (expected data volume, request or sample rate, concurrency,
hardware limits) become `OPEN` items citing the missing requirement — do not guess them.

Record the completed classification as a table (component, class, applicable or N/A with reason, decision,
budget or evidence) in section 9 of `pseudocode-architecture-template.md`. Never write to `plan/` directly.
